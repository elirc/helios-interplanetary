## 1. Why the OR defeats the index
`audit_resource(organization_id, resource_id, occurred_at)` can answer `resource_id=$2`. `details->>'incidentId'=$2` has no index.
A `BitmapOr` needs an index for **every** branch, so the planner falls back to scanning the tenant's rows
(via `audit_tenant_time` on `organization_id`, or a seq scan), evaluating the whole predicate per row, then sorting.
The cost is proportional to the tenant's total audit volume.

## 2. Selectivity and the partial index
Every reading writes `TelemetryRecorded` with `incidentId` in `details` (`telemetry.ts:140-148`). When no incident is active,
the value is JSON `null`, and `details->>'incidentId'` returns SQL `NULL`. Most rows are NULL, so index only the rest:
```sql
-- db/migrations/008-audit-incident-index.sql
CREATE INDEX audit_incident_ref ON audit_events (organization_id, (details->>'incidentId'), occurred_at)
  WHERE details->>'incidentId' IS NOT NULL;
```
The planner can use a partial index only if it can prove the query implies the `WHERE`. `details->>'incidentId' = $2` implies
`IS NOT NULL` (a strict operator), so the index qualifies. It works with generic plans too, because equality with a
parameter implies non-null. [Docker] Confirm with `EXPLAIN` that you get `BitmapOr` over `audit_resource` + `audit_incident_ref`.
With approach (a), neither query's text changes, so behaviour is trivially preserved. **This is the recommended answer** for the smallest safe diff.

## 3. The UNION alternative and its dedupe trap
```sql
SELECT … FROM audit_events WHERE organization_id=$1 AND resource_id=$2
UNION ALL
SELECT … FROM audit_events WHERE organization_id=$1 AND details->>'incidentId'=$2 AND resource_id <> $2
ORDER BY occurred_at DESC, id LIMIT 100
```
The `resource_id <> $2` in branch two removes rows that both branches match. Plain `UNION` dedupes on the **whole output row**
(here, the whole `eventJson` jsonb). That happens to work because `id` is inside it, but it costs a hash/sort over jsonb, and it
breaks silently if someone later projects without `id` (the agent tool's `action,details,occurred_at` projection has no `id`,
so two genuinely distinct events with identical content would collapse into one). Prefer `UNION ALL` + an explicit exclusion.
For top-N performance, put `ORDER BY … LIMIT` inside each branch as well: each branch walks its own index, and the outer query merges ≤ 2×N rows.

## 4. Determinism
`occurred_at DESC, id` is a total order. Plain `occurred_at` isn't: ties (the same `clock_timestamp()` is unlikely,
but a batch insert can create them) come back in any order, and `LIMIT 80` can cut a different event on each call.
The agent tool feeds an LLM, so non-deterministic context makes adviser runs harder to reproduce and evaluate.
Worth a follow-up ticket. It's **not** in scope here (behaviour is frozen), so a PR that "fixes" it has changed behaviour without asking.

## 5. Regression test
Seed one incident with events where both branches match, one where only `details.incidentId` matches, and one where only `resource_id` matches, plus more than 100 rows. Then assert:
- `getIncident(...).events` has length ≤ 100, is newest-first, has no duplicate ids, and includes the details-only event.
- `toolTx(c, p, "get_incident_timeline", {incidentId})` has length ≤ 80, is **oldest-first**, and returns exactly the keys `action,details,occurred_at`.
A merge of the two queries into one flips at least one of these assertions.

## Traps an agent typically falls into (use for adversarial review)
1. Changes only `queries.ts` and misses `agent-tools.ts:61`.
2. "De-duplicates" into one function and silently switches the tool to newest-100.
3. Writes a non-partial expression index (it works, but it's roughly as big as the table).
4. Uses `CREATE INDEX CONCURRENTLY` in a migration the runner wraps in a transaction (`src/server/migrations.ts:10`).
5. Claims "verified faster" from a demo-scale seed where a seq scan of 30 rows is optimal either way.
