## Answers to "explain before touching"
1. `migrate()` stores a sha256 of each file's text (`migrations.ts:17`) and throws `Applied migration 005-finance-support-security.sql changed. Add a new migration instead.`
   (`migrations.ts:22-23`) on any DB that already applied 005. Dev DBs break, and so does production on deploy. New file only.
   Related: the checksum is over raw text, so CRLF/LF differences also change it. This repo has a `.gitattributes`
   (astraspacegameweb doesn't, and crash-loops on exactly this, per its INC-004).
2. The equality column comes first, then the sort column: the B-tree gives "all of tenant X, already in created_at order", so `LIMIT 40` stops after 40 entries.
   `(created_at, organization_id)` would interleave all tenants by time.
3. `payment_attempts` lookups by invoice go through `UNIQUE(organization_id,invoice_id)`, which already serves them. Don't add an `invoice_id` index.
4. Each index adds one B-tree insert per row insert, inside the billing transactions. That's fine at this write volume. The reads are dashboard-hot, and the writes are per-invoice.
5. `SELECT … FROM journal_lines WHERE entry_id=journal_id` (`005:68`) runs in a deferred constraint trigger **per inserted row** (entries *and* lines).
   `journal_lines` has only `PRIMARY KEY(id)`, and Postgres doesn't index FK columns, so every journal insert seq-scans **all tenants'** journal lines at commit.
   It's O(total lines) per insert and gets worse forever. Fix: `CREATE INDEX journal_lines_entry ON journal_lines(entry_id)`. Or add `organization_id`
   to the trigger's predicate and index `(organization_id, entry_id)`, which also serves the hub join at `hub.ts:151` (explain-journal Q1).
   This is a **new finding** (not in `_answers/review.md`). It's reasoned, and [Docker] would confirm it with `EXPLAIN` inside the trigger via `auto_explain`.

## The CONCURRENTLY trap (the point of this ticket)
`migrate()` runs every file inside one `transaction(pool, …)` (`migrations.ts:10`), holding an advisory lock. Postgres rejects
`CREATE INDEX CONCURRENTLY` inside a transaction block (`ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block`).
So in this repo:
- Plain `CREATE INDEX` is what works. It takes a `SHARE` lock that blocks writes to that table for the build's duration.
  That's fine on demo data, and minutes of blocked invoice writes on a large table.
- A production answer: extend the runner with an opt-in "non-transactional migration" marker (a filename suffix or header comment) that runs
  outside the transaction and is idempotent (`CREATE INDEX CONCURRENTLY IF NOT EXISTS`, then check `pg_index.indisvalid`, because a failed
  concurrent build leaves an INVALID index behind). Or run the index out-of-band before deploying the migration that records it.
  See curriculum 07 (external apprenticeship curriculum, not in this repo).
